Rust rewrites: where they pay off, where they don't

The real question behind a Rust rewrite

Rust backend tutorials tend to show the same demo: a minimal HTTP server echoing JSON, a throughput number measured on a large machine, and a promise that memory safety eliminates whole classes of bugs. All of that is broadly true. What those demos leave out is the gap between a toy benchmark and a production service, and that gap is where rewrite projects get into trouble.

Rust removes entire categories of defects, and it also introduces new costs: borrow-checker friction that can stall feature work, async runtime complexity that leaks into every layer, and a compile-and-link cycle that feels slow when the work is business logic rather than systems code. None of these are reasons to avoid Rust. They are reasons to be specific about which services benefit.

The useful question is not "is Rust fast?" It is: for which backend workloads does a rewrite produce a measurable win, and for which does it become a multi-month detour that ships later and costs more to maintain? The deciding factor is usually whether the bottleneck is CPU-bound work that Rust can actually accelerate, or I/O-bound work where the language barely moves the needle.

Where the performance actually comes from

Rust's performance advantage in a backend context comes from three properties: no garbage collector, zero-cost abstractions, and compile-time memory safety that makes aggressive stack allocation practical.

The absence of a garbage collector matters most for latency shape, not average throughput. A service using a tracing or generational collector can see stop-the-world or concurrent-collection pauses that show up in tail latency. If a pause lands while a request is in flight, that request's latency includes the pause. Rust has no runtime collecting garbage during a request, so that particular tail-latency source disappears. This advantage only materializes if the workload allocates heavily or is CPU-bound. If the service spends most of its time waiting on a database query, the collector pause is not the dominant term in the latency budget, and rewriting the API layer will not make the database faster.

The second factor is the async model. Rust's async is poll-based rather than callback-based or green-thread-based. A work-stealing scheduler drives futures to completion, which is efficient, but it imposes a discipline: every async function returns a future that must be awaited, and blocking inside an async context stalls the worker thread that other tasks are scheduled on. A single blocking call in an otherwise non-blocking handler can collapse throughput, because the executor has a fixed number of worker threads (by default, one per available CPU core). Blocking one thread on a four-core machine removes a quarter of the executor's capacity; blocking all of them stops the service responding entirely.

So Rust works best when the design matches the runtime: non-blocking I/O throughout, CPU-heavy work offloaded to a blocking thread pool, and a clear boundary between async and synchronous code. When that discipline holds, the result is predictable latency and low memory use. When it does not, the result is a service that is harder to debug than the one it replaced.

A worked example: CPU-bound image resizing

Consider a service that accepts an image upload, produces three thumbnail sizes, and stores the results in object storage. Resizing is CPU-bound and parallelizable across cores. In a single-threaded-interpreter runtime, that work either blocks the event loop or is pushed to a thread pool, where a global interpreter lock limits true parallelism. Some image libraries release the lock during pixel operations and some do not, so scaling is sub-linear and hard to predict.

A Rust rewrite moves the same work into a blocking thread pool managed by the async runtime. The web layer can be built on a tower-based framework such as axum, with the async runtime underneath it and an image decoding/resizing crate for the pixel work. The essential detail is the offload:

use axum::{extract::Multipart, response::IntoResponse, routing::post, Router};
use image::{imageops::FilterType, ImageFormat};
use std::io::Cursor;
use tokio::task;

async fn upload(mut multipart: Multipart) -> impl IntoResponse {
    while let Some(field) = multipart.next_field().await.unwrap() {
        let data = field.bytes().await.unwrap();
        // Offload CPU-bound resizing to a blocking thread pool.
        let thumbnails = task::spawn_blocking(move || {
            let img = image::load_from_memory(&data).unwrap();
            let sizes = [(150, 150), (300, 300), (600, 600)];
            sizes.iter().map(|&(w, h)| {
                let resized = img.resize(w, h, FilterType::Lanczos3);
                let mut buf = Cursor::new(Vec::new());
                resized.write_to(&mut buf, ImageFormat::Jpeg).unwrap();
                buf.into_inner()
            }).collect::<Vec<_>>()
        }).await.unwrap();
        // Upload thumbnails to object storage here.
        for (_i, _thumb) in thumbnails.into_iter().enumerate() {
            // storage_client.put_object(...).send().await.unwrap();
        }
    }
    "OK"
}

#[tokio::main]
async fn main() {
    let app = Router::new().route("/upload", post(upload));
    let listener = tokio::net::TcpListener::bind("0.0.0.0:3000").await.unwrap();
    axum::serve(listener, app).await.unwrap();
}

Without spawn_blocking, the resize would occupy an executor worker and reduce the number of requests the service can make progress on. With it, the runtime schedules the work on a dedicated blocking pool and keeps the async workers free. On a four-core instance, the resizing work can proceed on roughly four cores in parallel, subject to how the blocking pool is sized and how much memory each resize needs.

The equivalent Python service is shorter and easier to read:

from fastapi import FastAPI, UploadFile
from PIL import Image
import io
import asyncio
from concurrent.futures import ThreadPoolExecutor

app = FastAPI()
executor = ThreadPoolExecutor(max_workers=4)

def resize_image(data: bytes):
    img = Image.open(io.BytesIO(data))
    sizes = [(150, 150), (300, 300), (600, 600)]
    results = []
    for w, h in sizes:
        resized = img.resize((w, h), Image.LANCZOS)
        buf = io.BytesIO()
        resized.save(buf, format="JPEG")
        results.append(buf.getvalue())
    return results

@app.post("/upload")
async def upload(file: UploadFile):
    data = await file.read()
    loop = asyncio.get_running_loop()
    thumbnails = await loop.run_in_executor(executor, resize_image, data)
    # upload to object storage...
    return {"status": "ok"}

The trade is visible in the two listings: the Rust version is more verbose and requires understanding of the runtime's scheduling model; the Python version is compact and its concurrency story is one line of run_in_executor. That verbosity is a real cost, paid at every review and every onboarding.

How to measure whether a rewrite is justified

Published throughput and latency figures for a rewrite are close to worthless, because they depend on the image sizes, the resize filter, the instance type, the storage backend, and the load generator. The honest approach is to measure your own service before and after. What to instrument:

  • CPU saturation on the existing service under production-like load. If CPU is well below saturation and latency is dominated by waiting, the language is not the bottleneck.
  • Tail latency percentiles (p50, p95, p99), not averages. Averages hide the pauses that motivate most rewrites.
  • Allocation rate and GC pause time if the current runtime has a collector. Many runtimes expose pause histograms; a language-level profiler will show allocation hot spots.
  • Time-in-request breakdown: how much of each request is CPU, how much is waiting on the database, and how much is waiting on outbound network calls.

Concretely: run the current service under a load generator that reproduces your real request mix, capture CPU profiles with a sampling profiler for your language, and record latency percentiles at the same time. Then build a minimal prototype of the hot path only, in Rust, and run the identical load against it on the same instance type. Compare p99 latency and CPU utilization at equal throughput, not peak throughput on an idle machine. If the prototype does not show a large, repeatable improvement on the CPU-bound portion of the request, the rewrite is not justified by performance.

It is worth stating the arithmetic explicitly. If a request spends 90% of its time waiting on a database and 10% on CPU, then even making the CPU portion infinitely fast improves end-to-end latency by at most 10%. If the same request spends 80% of its time in CPU-bound transformation, the ceiling on improvement is 80%, and a language change is a plausible way to approach it. Estimate the CPU fraction before writing any Rust; it bounds the entire project.

Failure modes that show up after launch

Blocking the async runtime. Using synchronous file APIs or a blocking HTTP client inside an async handler stalls an executor worker. The symptom is a service that handles a few requests fine and then hangs as load rises. The fix is to use async equivalents throughout, or wrap genuinely blocking calls in spawn_blocking. This is the single most common cause of "Rust is slow" reports.

The Send bound. Async functions must be Send to be spawned on a multi-threaded runtime. Holding a non-Send type across an await point produces a compile error about the future not being sendable between threads. This commonly arises from shared reference-counted types that are not thread-safe, or from holding a lock guard across an await. The fix is to use thread-safe equivalents and to scope lock guards so they are dropped before the await. The error message often points at a line far from the actual cause.

Dependency weight. A small web service can pull in a large dependency graph, which lengthens clean builds and grows the binary. cargo tree shows the graph and cargo bloat shows what contributes to binary size. This is manageable, but it is a recurring cost that a Python or Node service does not pay in the same form.

Unbounded concurrency. Spawning a task per request with no limit means outbound calls can exhaust file descriptors or trip provider rate limits. A semaphore around outbound work bounds concurrency. Without it, a traffic spike becomes a cascade.

Panics in request paths. unwrap() is fine in a prototype and dangerous in production. A panic in a request handler can abort the task; depending on configuration it may affect more than one request. Returning Result and handling errors at the boundary keeps a single bad input from becoming an outage.

Unpinned dependencies. For an application, the lockfile should be committed. Without it, a build in CI can resolve a newer crate version that changes behavior or fails to compile at the least convenient moment.

Decision checklist

Use this before committing engineering time:

  • Is the bottleneck CPU-bound and parallelizable, or is it waiting on I/O? If I/O dominates, stop here.
  • What fraction of end-to-end latency is CPU? That fraction is your ceiling on improvement.
  • Does the current runtime show collector pauses in the tail latency you care about?
  • Does the team already have production Rust experience, or is this a first project? A first project should be one isolated endpoint, not a service.
  • Can you deploy the Rust service alongside the existing one and route a fraction of traffic to it?
  • Is there a plan to measure p99 latency and CPU utilization at equal throughput, on the same instance type, with the same request mix?
  • What is the maintenance cost of the new service — build times, dependency updates, on-call familiarity?

If the answers point to a CPU-bound hot path, an existing deployment path for a sidecar service, and at least one engineer comfortable with async Rust, a scoped rewrite is reasonable. If not, optimizing the current service is usually the better return.

Frequently asked questions

How does Rust compare to Go for backend services? Go has a simpler concurrency model, faster compiles, and a garbage collector that is adequate for most services. Rust offers lower memory overhead and no collector pauses, at the cost of more complexity in the type system and async model. For latency-sensitive CPU-bound work, Rust has the edge. For rapid iteration and a large hiring pool, Go is often the pragmatic choice.

Why does a Rust service show high CPU and low throughput? The most likely cause is blocking the async runtime. Check for synchronous file or network calls inside async handlers, and for CPU-heavy work that is not wrapped in spawn_blocking. Runtime introspection tools can show whether tasks are stuck. The fix is to offload blocking work to a thread pool or replace it with async equivalents.

What is the best way to handle database connections? Use a connection pool rather than opening a connection per request. A pool handles reuse, health checks, and acquisition timeouts. Set a maximum pool size that matches the database's connection limit divided by the number of service instances, and set an acquisition timeout so requests fail fast rather than hanging when the pool is exhausted.

When should a Python or Node service not be rewritten in Rust? When the workload is I/O-bound, when the team lacks Rust experience, or when the deadline is tight. A rewrite for a small single-digit performance gain rarely pays for the added complexity. Rewrite when the CPU-bound fraction is large and the measured improvement is substantial and repeatable.

Do this next

Before writing any Rust, profile the service you already have. Pick one endpoint that you suspect is CPU-bound, run it under production-like load, and capture a CPU profile alongside p50/p95/p99 latency. Then compute the CPU fraction of the request: if it is small, stop and optimize elsewhere. If it is large, build a prototype of that single endpoint in Rust and run the same load against it on the same instance type at equal throughput. Compare the tail latency and CPU utilization numbers side by side. That comparison — not a benchmark from a tutorial — is the evidence that should decide whether the rewrite proceeds.
