Context windows: agents that run for days

Long-running agents fail when context is treated as a log. Keep constraints verbatim, checkpoint durable state, and cap the working set per cycle.

The one-paragraph version

A long-running agent has a context window that fills up. The naive fix — summarize old turns and keep going — works for a few hours and then fails in a way that is hard to debug: the agent forgets a constraint it was given early on, re-reads a file it already modified, or hallucinates a tool result that never happened. The more robust approach is to stop treating the context window as a log and start treating it as a working set. Keep a small, structured state object outside the prompt, retrieve only the slices needed per step, and let the raw transcript age out. The part that trips people up is that "summarize and continue" looks like it preserves state when it actually destroys the exact details agents depend on.

Why this concept confuses people

When you build a chatbot, the context window is basically a conversation. Turn 1, turn 2, turn 3, all appended. It grows, you hit the limit, you truncate the oldest turns, done. That mental model is correct for chat and wrong for agents, and the confusion comes from the fact that both use the same API shape.

An agent is not a conversation. It is a loop: observe, decide, act, observe. Each iteration appends a tool call and a tool result. A single read_file on a 2,000-line source file can burn more tokens than the entire preceding conversation. A grep that returns 400 matching lines can do the same. Over a multi-hour run, the transcript is dominated not by reasoning but by tool output — and tool output is the least useful thing to keep around once you have extracted what you needed from it.

Here is the trap. Teams hit the limit, reach for summarization, and the summary drops the things that matter. A common failure mode: an agent is told at step 4 that the staging database is read-only and it must not run migrations. By step 300, that constraint has been summarized into "working on staging database tasks." The agent then runs a migration. Nothing in the summary was wrong, exactly. It just was not load-bearing.

There is a second source of confusion: people conflate the model's context limit with the agent's memory. They are different. The context limit is a hard wall — for example, 128k tokens on GPT-4o, 200k on Claude 3.5 Sonnet, 1M on Gemini 1.5 Pro. Memory is whatever you decide to persist outside that wall. If your only memory is the context window, you do not have memory, you have a buffer.

The mental model that makes it click

Think of it like a chef working a 12-hour service. The context window is the counter in front of them. It holds what they are actively working on: the ticket they are plating, the ingredients for that dish, the pan on the burner. It does not hold the entire walk-in fridge, and it should not — you cannot cook on a counter that is also a warehouse.

The walk-in fridge is your external state. It is a database, a JSON file, a Redis key, a vector store, whatever fits. The chef walks over, grabs what they need for this ticket, comes back. The counter stays small.

The mistake most teams make is treating the counter as the fridge. They keep piling things on it because "the model might need it later." It will not need all of it. It needs the specific things relevant to the current step, and the skill is knowing which those are.

So the model is: external state + retrieval + bounded working set. Three pieces.

External state is a structured record of facts the agent has established: file paths it has touched, decisions it has made, constraints it was given, results it has committed. It is small. It is queryable. It survives process restarts, which matters when your agent runs for three days and the worker gets OOM-killed at hour 40.

Retrieval is how you pull slices of that state into the prompt. Sometimes it is a simple key lookup ("give me the constraints list"). Sometimes it is semantic search over past tool results. Sometimes it is just "the last 5 actions."

Bounded working set is the discipline of capping what actually goes into the prompt per step. You decide a budget — say 8k tokens for context, 4k for the current task — and you enforce it. When something does not fit, it gets summarized or dropped, and you decide which, explicitly, per category.

A concrete worked example

Consider an agent that monitors a codebase and opens PRs for dependency updates. It runs continuously, checks for new releases every 30 minutes, and when it finds one it reads the changelog, checks the repo for usage, and either opens a PR or logs "skip."

Run that for a week and you will process roughly 300 updates. If you append everything to context, you are looking at 300 changelogs plus 300 grep results plus 300 decisions. At an average of 1,500 tokens per cycle, that is about 450k tokens (300 cycles × 1,500 tokens) — well past most models' limits, and even on a 1M-token model you are paying for tokens that are mostly irrelevant to the current decision.

The fix is to split state into three stores:

  1. Decisions log — append-only, structured. {package, version, action, reason, timestamp}. One line per cycle. This is what you retrieve when the agent needs to know "have I already handled this?"
  2. Constraints — a small, stable list. "Do not touch packages in the @internal/* scope." "Major version bumps require a human review flag." This never gets summarized; it is always injected verbatim, because it is the thing summarization destroys.
  3. Working context — the current cycle only. Changelog for this package, grep results for this package, the relevant package.json lines. Discarded when the cycle ends.

Here is a minimal version of that in Python, using a plain SQLite file for state (no vector DB needed for this shape):

import sqlite3
import json
from datetime import datetime, timezone

DB = "agent_state.db"

CONSTRAINTS = [
    "Never modify packages under @internal/* scope.",
    "Major version bumps must set requires_human_review=True.",
    "If changelog mentions a breaking change, skip and log.",
]

def init_db():
    conn = sqlite3.connect(DB)
    conn.execute("""
        CREATE TABLE IF NOT EXISTS decisions (
            package TEXT, version TEXT, action TEXT,
            reason TEXT, ts TEXT,
            PRIMARY KEY (package, version)
        )
    """)
    conn.commit()
    return conn

def already_handled(conn, package, version) -> bool:
    row = conn.execute(
        "SELECT 1 FROM decisions WHERE package=? AND version=?",
        (package, version),
    ).fetchone()
    return row is not None

def build_prompt(conn, package, version, changelog, grep_hits):
    # Bounded working set: constraints always, recent decisions only.
    recent = conn.execute(
        "SELECT package, version, action FROM decisions "
        "ORDER BY ts DESC LIMIT 20"
    ).fetchall()

    return {
        "constraints": CONSTRAINTS,          # never summarized
        "recent_decisions": recent,          # last 20, hard cap
        "current_task": {                    # discarded after this cycle
            "package": package,
            "version": version,
            "changelog": changelog[:4000],   # truncate, don't summarize
            "grep_hits": grep_hits[:50],
        },
    }

def record(conn, package, version, action, reason):
    conn.execute(
        "INSERT OR REPLACE INTO decisions VALUES (?,?,?,?,?)",
        (package, version, action, reason,
         datetime.now(timezone.utc).isoformat()),
    )
    conn.commit()

Three things to notice. First, constraints are injected verbatim every cycle — no summarization, ever. Second, the working set is truncated by character count, not summarized. Truncation is lossy but predictable; summarization is lossy and unpredictable, and unpredictability is what kills long runs. Third, the decisions table is the actual memory, and it is tiny — a week of cycles is roughly 300 rows, a few hundred KB.

A common failure mode here is forgetting to cap recent_decisions. Six months in, that LIMIT 20 query is fine, but if someone "improves" it to "all decisions" to give the agent more history, you are back to the same problem. Cap everything that goes into the prompt.

How this connects to things you already know

If you have done any backend work, this is a cache eviction problem. The context window is your L1 cache. External state is your database. Retrieval is your cache-miss handler. You already know that you do not put the whole database in L1, and you already know that LRU is not always right.

The specific eviction policy matters, and it is where the analogy gets useful. For a long-running agent, you want something closer to category-based eviction than LRU. Constraints never evict. Decisions evict by recency. Tool results evict by relevance-to-current-task. Raw transcripts evict immediately after the step that produced them.

It is also the same shape as a stream processor's state management. If you have used Kafka Streams or Flink, you know that a long-running stream operator cannot keep everything in memory — it keeps a bounded state store and checkpoints it. Agent state is the same: bounded, checkpointed, recoverable.

And it is the same as session management in a web app. You do not put the whole user session in a cookie. You put a session ID, and the server looks up the rest. Your agent's prompt should include a state pointer, not the state itself.

Common misconceptions, corrected

"Bigger context windows solve this." They delay it. A 1M-token window at 300 cycles still fills in a few days. More importantly, models can degrade on long contexts — the "lost in the middle" effect is documented, where information in the middle of a long prompt is retrieved less reliably than information at the start or end. Even if you fit, you may lose. Long-context prompting guidance commonly recommends putting key instructions at the beginning and end for exactly this reason.

"Summarization is memory." Summarization is compression, and compression is lossy in ways you cannot predict. A summary of "the agent worked on authentication" loses "the agent must not touch the OAuth token refresh path." The constraint is what matters; the summary is what survives.

"Vector search over the transcript is enough." It helps, but it is a retrieval layer over a growing pile, not a replacement for bounded state. You still need to cap what goes in. A vector store that returns 50 chunks per query is just a slower way to blow your context budget.

"The agent should just remember." Models do not remember between calls. Every call is stateless. If you are not persisting state explicitly, it does not exist.

"Tool results should be kept for audit." Audit them to a log file, not to the prompt. The audit log and the working set are different artifacts with different lifetimes.

The advanced version (once the basics are solid)

Once you have external state and bounded working sets, the next problems are retrieval quality and checkpointing.

Retrieval quality: a flat LIMIT 20 on decisions works until it does not. When an agent handles 20 different packages and needs to know about package #3 specifically, recency is the wrong axis. The fix is hybrid retrieval — filter by entity ("decisions where package = lodash") first, then rank by recency within that. This is a SQL WHERE clause, not a vector search, for structured state. Vectors are for unstructured state like changelog text where you do not have a clean key.

Checkpointing: a 3-day run will survive process restarts, deploys, and OOM kills. If your state is only in memory, you lose it. SQLite (as above) is fine for single-writer agents. For concurrent agents, a Redis instance with AOF persistence or a Postgres instance both work; Redis is faster for the read-heavy pattern, Postgres is better if you want transactional guarantees across multiple state tables.

Here is a checkpoint pattern using Redis that survives a worker restart mid-cycle:

import { createClient } from 'redis';

const redis = createClient({ url: process.env.REDIS_URL });
await redis.connect();

const CYCLE_TTL_SECONDS = 60 * 60 * 6; // 6 hours, generous for one cycle

async function checkpoint(agentId, cycleState) {
  // Working set: TTL'd, gone after the cycle.
  await redis.set(
    `agent:${agentId}:cycle`,
    JSON.stringify(cycleState),
    { EX: CYCLE_TTL_SECONDS }
  );
  // Durable state: no TTL, survives restarts.
  await redis.hSet(`agent:${agentId}:decisions`, {
    [cycleState.package]: JSON.stringify({
      version: cycleState.version,
      action: cycleState.action,
      ts: Date.now(),
    }),
  });
}

async function resume(agentId) {
  const raw = await redis.get(`agent:${agentId}:cycle`);
  if (!raw) return null; // cycle completed or expired; start fresh
  return JSON.parse(raw);
}

The distinction between the two Redis keys is the whole point. The cycle key has a TTL because it is scratch space. The decisions hash has no TTL because it is the agent's actual memory. Getting this backwards — TTL on decisions, no TTL on cycle — produces an agent that forgets everything and a Redis instance that fills with garbage.

One more advanced concern: token accounting. Log prompt token counts per cycle. A healthy long-running agent typically stays under 10k input tokens per cycle even at hour 200. If you see it creeping toward 40k, something is leaking into the working set. That is your alarm.

How to measure your own context behavior

The table above is a set of hypotheses, not a benchmark. To get real numbers, instrument the loop.

  1. Log input token count per cycle. Most provider SDKs return usage metadata on each response (for example, response.usage.input_tokens on the OpenAI and Anthropic APIs). Write it to a structured log line: {cycle, agent_id, input_tokens, output_tokens, timestamp}.
  2. Log the size of each prompt category. Before you send the request, record how many characters went into constraints, decisions, tool results, and reasoning. A few lines of code around your build_prompt function is enough.
  3. Plot input tokens over cycle index. A flat line is healthy. A line with positive slope means something is leaking into the working set. A step function means a category was added or a cap was removed.
  4. Compare against a baseline. Run the agent for 50 cycles with your caps in place, then remove one cap (for example, set LIMIT 20 to LIMIT 1000) and run again. The difference in input tokens tells you the marginal cost of that category.
  5. Track task success rate, not just tokens. A cheaper prompt that fails more often is not a win. Log whether each cycle produced the intended outcome (PR opened, skip logged, error raised) and compare success rate across configurations.

The specific commands depend on your stack, but the pattern is universal: emit structured events from the agent loop, ship them to whatever you already use for logs (stdout, a log aggregator, a metrics backend), and query them. If you do not have a metrics backend, a CSV file and a plotting library will do for the first week.

Quick reference

  • Context window is a working set, not a log. Cap it explicitly per cycle.
  • Constraints go in verbatim, every cycle. Never summarize them.
  • Decisions go in a structured store (SQLite, Redis with AOF, Postgres). Query by entity, not just recency.
  • Tool results are scratch. Truncate by character count, do not summarize.
  • Working set gets a TTL. Durable state does not. Getting this backwards is a common bug.
  • Log prompt tokens per cycle. A creeping input token count on a simple agent means a leak.
  • Models can degrade on long contexts (lost-in-the-middle). Fitting is not the same as working.
  • Every model call is stateless. If you did not persist it, it is gone.

Frequently Asked Questions

How many tokens can a long-running agent actually use before it degrades?

It is not a hard number, and it depends on the model, the task, and how the context is arranged. Quality degradation on long contexts has been observed well before the model's stated limit in published evaluations of the lost-in-the-middle effect. The practical move is to keep per-cycle input small — many teams target under 10k tokens — regardless of the model's ceiling. That gives you headroom and keeps you in the region where retrieval is reliable. Measure your own degradation by running the same task with prompts of increasing length and comparing success rate.

Why does my agent forget instructions I gave it at the start?

Because those instructions got summarized or evicted as the transcript grew. If you are using summarize-and-continue, the summarizer has no way to know which details are load-bearing. The fix is to move constraints out of the transcript entirely and inject them verbatim on every call. They are small — a few hundred tokens — and they are the one category that should never be compressed.

Should I use a vector database for agent memory?

Only for unstructured history where you do not have a clean key. If you can answer "what do I need?" with a SQL WHERE clause, use SQL. Vector search adds latency and returns fuzzy results, which is the wrong tradeoff for structured state like decisions and constraints. Use vectors for "find past changelogs that mentioned breaking changes," not for "what is the status of package lodash."

How do I handle an agent that runs for days and gets killed mid-cycle?

Checkpoint the cycle state to a TTL'd key and the durable decisions to a non-TTL store, as in the Redis example above. On startup, try to resume the cycle; if the key expired, start fresh. The important part is idempotency: recording a decision twice should be a no-op (INSERT OR REPLACE or HSET), so a restart mid-write does not corrupt state. If your agent cannot survive a kill -9 at any point, it is not ready to run for days.

Do I need a separate process for state, or can I keep it in the agent?

For a single agent on a single host, an embedded store like SQLite is enough and avoids operational overhead. You need a separate process (Redis, Postgres, or similar) when multiple agents share state, when the agent runs on ephemeral compute like containers or serverless, or when you need the state to outlive the agent host. The decision is about failure domains, not performance.

A decision checklist before you ship a long-running agent

  • Can the agent survive a kill -9 at any point in its loop and resume correctly?
  • Are constraints stored outside the transcript and injected verbatim on every call?
  • Is every category that enters the prompt capped by an explicit limit?
  • Is there a log line emitting input token count per cycle?
  • Is durable state stored separately from scratch state, with different TTLs?
  • Can you query decisions by entity (package, file, user), not just by recency?
  • Have you measured task success rate at your current context size, not just assumed it?
  • Do you have an alarm for input tokens trending upward over time?

Do this in the next 30 minutes: open your agent's main loop file and find where you build the prompt. Count the categories of things you are putting in. If constraints and tool results are in the same list, split them — pull constraints into a module-level constant that gets injected verbatim, and cap tool results with a character slice. Then add one log line printing the input token count per cycle. That single number will tell you within a day whether you have a leak.
