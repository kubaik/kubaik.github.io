Flaky tests: reliability bug, not test noise

Flaky tests usually point to real non-determinism in production code. Learn to classify the four families, triage by blast radius, and fix the source.

A flaky test is a test that passes and fails on the same code. The instinct is to treat it as a testing problem — rerun it, tag it, skip it, move on. That instinct is usually wrong. A flaky test is a signal that something in the system is non-deterministic, and non-determinism does not care whether it is being observed by a test. The same race condition that makes an assertion fail intermittently will, under different timing, corrupt a record, drop a message, or return stale data to a user. The test is not the problem; the test is the smoke detector.

This article explains why flakiness is a production reliability signal, how to classify the underlying causes, and how to triage them systematically.

Why flakiness gets misread

The confusion starts with where the failure appears. When a test fails, the failure surfaces in the test suite. When it passes on rerun, the suite goes green. The feedback loop teaches a specific lesson: the test is unreliable. From there, the natural fixes are all test-side — increase the timeout, add a retry, mark it @flaky, quarantine it. Each of those fixes makes the suite greener without touching the code under test.

There is a second source of confusion: the word "flaky" is used for at least four different phenomena that have almost nothing in common. A test that depends on wall-clock time, a test that depends on shared mutable state, a test that depends on network ordering, and a test that depends on an unseeded random number generator all get filed under the same label. They need different fixes, and only some of them indicate a production bug.

The third source is organizational. Test suites are usually owned by whoever wrote them, and flaky tests are usually owned by nobody. A failing test blocks a merge, so the fastest path to unblocking is to make the test stop failing. The incentive structure rewards silencing the signal, not investigating it. That is a process problem masquerading as a technical one.

The real cost: teams routinely delete or quarantine the one signal that would have told them, weeks before an incident, that a code path was timing-dependent.

The mental model that makes it click

Think of a test suite like a canary in a coal mine. The canary is not the hazard; the canary is the sensor. If the canary dies, you do not replace the canary and go back to work — you evacuate. A flaky test is a canary that dies intermittently. Intermittent death is not better news than consistent death; it is arguably worse, because it tells you the hazard is timing-dependent and therefore harder to reproduce.

The useful reframe: a test is a deterministic function of the system state. If the same code and the same inputs produce different outputs, then either the inputs are not the same (hidden state) or the function is not deterministic (a race, an unseeded RNG, a clock dependency, an external service). Both of those are properties of the system, not of the test.

There is one important exception. A test can be flaky because the test itself is badly written — for example, it asserts on a log line that is written asynchronously by a background thread the test does not join. In that case the flakiness is genuinely test-side. The skill is telling the two apart, and the default assumption should be that the system is at fault until proven otherwise. Test-side flakiness is real but rarer than teams assume, and assuming it first is how real bugs get buried.

A useful heuristic: if the test fails in CI but passes locally, ask what is different about the environments. If the answer is "nothing I can name," that is itself the finding — you have an unnamed environmental dependency.

The four families of flakiness

Almost every flaky test falls into one of four families. The family determines both the production risk and the fix.

1. Time and clock dependencies

The test uses the real clock — System.currentTimeMillis(), time.time(), Date.now(), datetime.now() — or depends on a timeout that is too tight for a loaded CI machine. The production risk depends on whether the production code also uses the real clock in a way that matters. A test that sleeps 100ms and asserts a result is test-side flakiness. A test that exposes a production code path using now() to decide whether a token is expired is a production bug: the same code will misjudge expiry under load.

2. Shared mutable state and ordering

Tests that share a database, a cache, a global singleton, or a temp directory can interfere with each other. When tests run in parallel or in a different order, interference changes. The production risk is high: shared mutable state in tests usually mirrors shared mutable state in production, and the same interleaving that breaks a test can break a request.

3. Concurrency and races

Tests that start a thread, a goroutine, an async task, or a background worker and then assert on its output without a proper join or synchronization primitive. These are the highest-signal flakes. A race the test can hit is a race production can hit; production just has more traffic and more chances.

4. External dependencies and network

Tests that hit a real network, a real queue, a real third-party API, or a real DNS resolver. Some of this is unavoidable in integration tests, but if a test is flaky because a dependency is slow, the fix is usually to inject a fake — which also makes production code more testable and more resilient. The production risk is moderate: the system may genuinely be fragile to dependency latency, in which case the flake is telling you something.

Family Typical symptom Production risk Usual fix
Clock Passes locally, fails in CI around midnight or on slow machines Low if test-only, high if production uses real clock for decisions Inject a clock; make time a parameter
Shared state Fails only when run with other tests, passes in isolation High — mirrors production shared state Isolate state per test; use transactions or unique namespaces
Concurrency Fails rarely, often on CI with different core counts Highest — same race exists in production Fix the race in production code; do not paper over with sleeps
External deps Fails when a dependency is slow or down Moderate — may indicate missing timeouts or retries Inject fakes; add timeouts and circuit breakers in production

A worked example

Consider a small Python service that processes jobs from a queue and writes results to a database. A test asserts that after enqueueing a job, the result row exists within one second.

import time
import threading
from queue import Queue

class Worker:
    def __init__(self, db):
        self.db = db
        self.queue = Queue()
        self._stop = threading.Event()
        self._thread = threading.Thread(target=self._run, daemon=True)

    def start(self):
        self._thread.start()

    def stop(self):
        self._stop.set()
        self._thread.join(timeout=2)

    def enqueue(self, job):
        self.queue.put(job)

    def _run(self):
        while not self._stop.is_set():
            try:
                job = self.queue.get(timeout=0.1)
            except Exception:
                continue
            result = process(job)
            self.db.write(result)

A naive test:

def test_job_writes_result(db):
    worker = Worker(db)
    worker.start()
    worker.enqueue({"id": 1})
    time.sleep(1)  # hope the worker finishes
    assert db.get(1) is not None

This test is flaky on a loaded CI machine. The instinct is to raise the sleep to five seconds. That makes the flake rarer without fixing anything. The real issue is that the test has no way to know when the write has happened, and the production code has no way to signal it. Add a completion event:

class Worker:
    # ... same as before ...
    def __init__(self, db):
        self.db = db
        self.queue = Queue()
        self._stop = threading.Event()
        self._done = {}  # job id -> threading.Event
        self._lock = threading.Lock()
        self._thread = threading.Thread(target=self._run, daemon=True)

    def enqueue(self, job):
        with self._lock:
            self._done[job["id"]] = threading.Event()
        self.queue.put(job)

    def wait_for(self, job_id, timeout=5):
        with self._lock:
            ev = self._done.get(job_id)
        if ev is None:
            raise KeyError(job_id)
        if not ev.wait(timeout):
            raise TimeoutError(f"job {job_id} did not complete")

    def _run(self):
        while not self._stop.is_set():
            try:
                job = self.queue.get(timeout=0.1)
            except Exception:
                continue
            result = process(job)
            self.db.write(result)
            with self._lock:
                ev = self._done.get(job["id"])
            if ev is not None:
                ev.set()

And the test:

def test_job_writes_result(db):
    worker = Worker(db)
    worker.start()
    worker.enqueue({"id": 1})
    worker.wait_for(1, timeout=5)
    assert db.get(1) is not None

Notice what changed. The test is now deterministic. More importantly, the production code now has a way to report completion, which means callers can wait for a job instead of polling or sleeping. The flaky test was pointing at a missing capability in the production API. Fixing the test properly fixed the production code.

This is the pattern to internalize: a flaky test is often an interface that has not been designed yet. The test is trying to synchronize with something the production code does not expose.

Measuring whether the fix worked

A fix is only credible if it is measured. The instrumentation is straightforward and does not require a special framework:

  1. Record, per test, the outcome of every run, keyed by test ID and commit SHA. Most CI systems already store this; if not, a small script that parses the JUnit XML or equivalent report and appends rows to a table is enough.
  2. Compute flake rate per test as (failed runs) / (total runs) over a rolling window, for example 30 days or the last 500 runs, whichever comes first.
  3. Compare the window before and after the fix. A concurrency fix should drive the rate to zero across a window large enough to have contained at least a few prior failures. If the test failed roughly once per 200 runs before, a 500-run window with zero failures is weak evidence; a 2000-run window with zero failures is stronger.
  4. Track the aggregate: number of distinct flaky tests per week, and total retries per week. Both should trend down if triage is working.

The point of the measurement is not to produce a dashboard. It is to distinguish "the flake got rarer" from "the flake is gone," because those two outcomes have very different implications for production.

How this connects to things you already know

If you have ever debugged a production incident that "only happens under load," you have already met the family of bugs that flaky tests detect. Load is a timing amplifier. A race that needs a specific interleaving to manifest appears rarely in tests and frequently in production, because production runs the code path millions of times.

The connection to observability is also direct. A flaky test is essentially a unit-level alert. If you would not silence a production alert by deleting the alert rule, you should not silence a flaky test by deleting the test. Both are the same move: removing the sensor because you do not like the reading.

The connection to CI cost is worth naming too. Teams often justify quarantining flaky tests by pointing at wasted CI minutes. That is a real cost, but it is the smaller one. The larger cost is the incident that ships because the test that would have caught it was quarantined weeks earlier. CI minutes are visible; averted incidents are not, which is exactly why the trade-off is misjudged.

Common misconceptions, corrected

"It's just the test environment." Sometimes. But the test environment is also a computer running your code. If the code behaves differently on a loaded machine, it will behave differently on a loaded production machine. The environment is part of the system.

"Retries make flaky tests fine." Retries make the suite green. They do not make the code deterministic. A retry is a bet that the flake is environmental, and that bet is wrong often enough that it should be a deliberate decision, not a default. If you do add retries, log every retry with the test name and the failure reason, and treat a rising retry rate as a production risk indicator.

"Flaky tests are a test-suite problem." They are a test-suite symptom. The problem lives in the code under test until you prove otherwise.

"We'll fix it later." Later is when the test is deleted by someone under deadline pressure who has no context. If a flake is not triaged within a sprint, the default outcome is deletion, not repair.

"It only fails rarely, so it's low priority." The flake rate of the test and the failure rate of the production path are not the same number. As an illustrative example: a test that fails once per 1000 runs, covering a code path executed 10 million times per day, corresponds to roughly 10,000 production executions per day hitting the same non-determinism — assuming the test's execution conditions resemble production's. They usually do not resemble them exactly, which means the production number can be higher or lower; the point is that it is not bounded by the test's flake rate.

Triage framework

Once flaky tests are accepted as reliability signals, the question becomes how to triage them systematically. A workable framework has three axes: blast radius, reproducibility, and family.

Blast radius asks what production code the test exercises. A flake in a test of a pure function is low blast radius. A flake in a test of a payment state machine is high blast radius. Prioritize by blast radius, not by flake frequency.

Reproducibility asks whether the flake can be made deterministic. The best tool here is not more test runs — it is a deterministic scheduler or a fault-injection harness. Some languages and runtimes offer deterministic concurrency testing tools; if yours does not, orderings can still be forced by injecting synchronization points into the code under test behind a test-only flag. The goal is to turn a rare flake into a reliable reproduction.

Family tells you the fix. Clock flakes get a clock injection. Shared-state flakes get isolation. Concurrency flakes get the race fixed. External-dependency flakes get fakes and production timeouts.

A practical triage policy that teams have found workable:

  • Every flaky test gets an owner and an issue within one working day. No anonymous flakes.
  • Quarantine is allowed only with a linked issue, an owner, and an expiry date. Quarantine without an expiry is deletion with extra steps.
  • Retries are allowed only on tests explicitly classified as external-dependency flakes, and the retry count and reason are logged.
  • A flake in a high-blast-radius test blocks the release until triaged, the same way a failing test does.
  • When a flake is resolved, the fix is recorded against the family it belonged to, so patterns across the suite become visible over time.

Failure modes of the triage process itself

Even a well-designed triage process has predictable failure modes, and naming them in advance makes them easier to catch:

  • Quarantine creep. Quarantined tests accumulate because expiry dates are not enforced. Mitigation: make expiry a CI check that fails the build when a quarantine entry is past due.
  • Owner churn. The assigned owner leaves or changes teams, and the issue sits. Mitigation: assign ownership to a team, not an individual, and review open flake issues on a fixed cadence.
  • Retry laundering. Retries get added to more tests over time because they are cheap and effective at greening the suite. Mitigation: require a classification label before a retry is permitted, and audit the labels periodically.
  • Blast-radius inflation. Everything gets marked high blast radius and the priority ordering collapses. Mitigation: define blast radius concretely — for example, by which user-facing endpoints the covered code serves — rather than by intuition.

Frequently asked questions

How do I tell if a flaky test is a production bug or just a bad test? Ask whether the test's non-determinism comes from the code under test or from the test harness. If the production code uses a real clock, shared state, or unsynchronized concurrency, the flake is a production signal. If the test only fails because it asserts on something asynchronous it does not join, it is test-side. The default assumption should be production until proven otherwise.

Why do flaky tests often pass locally but fail in CI? CI machines are usually more loaded, have different core counts, and run tests in a different order or in parallel. All of those change timing and interleaving, which is exactly what non-deterministic code is sensitive to. The difference between local and CI is not a reason to dismiss the flake; it is a clue about which family it belongs to.

Is it ever acceptable to delete a flaky test? Only after triage has shown the test is genuinely test-side and the cost of fixing it exceeds the value of keeping it. Deleting before triage is the failure mode this whole article is about. If a test must be removed, link the issue that explains why, so the decision is reviewable later.

What is the single best first step for a team with many flaky tests? Stop allowing silent retries. Make every retry log the test name and failure reason, and make the retry rate visible. That one change converts an invisible problem into a measurable one, and measurement is the precondition for every other fix.

  • Four families: clock, shared state, concurrency, external dependency.

  • Default assumption: the system is at fault, not the test.
