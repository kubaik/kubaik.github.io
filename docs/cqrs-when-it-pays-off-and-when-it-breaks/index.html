CQRS: when it pays off and when it breaks

CQRS adds eventual consistency and projection lag. Learn the specific errors that mean it&#x27;s overkill, and when a read replica beats it.

The error and why it's confusing

You've probably seen this one: after deploying a CQRS-based service, your read model lags behind the write model, and users complain that their updates don't appear. Or worse, you get a 409 Conflict from your API gateway because two commands hit the same aggregate simultaneously. The error message might be something like OptimisticConcurrencyException: The aggregate was modified by another process or CommandHandlerTimeout: The command did not complete within 5000ms. These errors are confusing because they don't point to a single misconfiguration — they point to a fundamental mismatch between your domain's consistency requirements and the architectural pattern you chose.

CQRS (Command Query Responsibility Segregation) separates writes from reads. In theory, it lets you scale each side independently and use different data models. In practice, it introduces eventual consistency, message duplication, and a whole new class of failure modes. The part that trips people up is that CQRS isn't a binary choice — it's a spectrum, and the errors you see are often symptoms of applying it at the wrong level of granularity. This post covers the specific failure modes that indicate CQRS is hurting more than helping, and how to tell whether your project is one where it earns its complexity.

What's actually causing it (the real reason, not the surface symptom)

The surface symptom is usually a stale read or a command timeout. The real reason is almost always one of three things:

  1. You're using CQRS for a domain that doesn't have asymmetric read/write loads. If your application reads and writes roughly the same amount of data, and both operations are simple CRUD, CQRS adds latency and complexity without benefit. A typical example: an internal admin tool that processes 100 writes per minute and 200 reads per minute. Splitting that into separate models means you now need a message broker, a projection engine, and a way to handle failures in the projection pipeline — all for a system that could run on a single PostgreSQL instance with 4 vCPUs and 16 GB RAM.

  2. You're using CQRS to solve a consistency problem that should be solved with transactions. A common trap is using CQRS to avoid database locks. But if your business rules require that a write is immediately visible to a read (e.g., a user updates their profile and expects to see the change on the next page load), eventual consistency is the wrong tool. You end up adding compensating transactions and reconciliation jobs that are harder to maintain than a simple SELECT ... FOR UPDATE.

  3. Your read model is not idempotent. When projections fail and messages are redelivered, non-idempotent handlers cause duplicate rows, incorrect aggregates, or corrupted state. This is especially common when using event sourcing with CQRS. A typical failure: a UserCreated event is processed twice, and your read model inserts two user records with the same ID, causing a unique constraint violation that halts the entire projection.

These root causes manifest as specific errors. For example, a DuplicateKeyException in your read database after a broker redelivery, or a TimeoutException when a command handler waits for a projection to catch up before returning. The confusion comes from treating these as infrastructure bugs when they're actually architectural mismatches.

Fix 1 — the most common cause

The most common cause is using CQRS where a simple read replica would suffice. Teams often adopt CQRS because they've heard it's the way to scale reads. But if your read load is high and write load is low, you can often just add a read replica to your existing database and route read queries there. This gives you most of the scaling benefit with none of the eventual consistency complexity.

Symptom pattern: You see high read latency on your primary database, so you split reads to a separate model. But now your application code has two data access paths, and you're constantly writing projection logic. The error you see is often ReadModelNotUpToDateException or a user complaint that their changes aren't visible.

Fix: Before committing to CQRS, measure your read/write ratio. If reads are less than 10x writes, a read replica is almost always simpler. For example, a typical e-commerce product catalog might have a 100:1 read/write ratio, which justifies CQRS. But a user profile service with a 2:1 ratio does not.

Here's a Python example using SQLAlchemy 2.0 to route reads to a replica while keeping writes on the primary. This is not CQRS — it's just read/write splitting, and it solves the same scaling problem without eventual consistency:

from sqlalchemy import create_engine
from sqlalchemy.orm import sessionmaker

# Primary for writes
write_engine = create_engine("postgresql://user:pass@primary:5432/db")
# Replica for reads
read_engine = create_engine("postgresql://user:pass@replica:5432/db")

WriteSession = sessionmaker(bind=write_engine)
ReadSession = sessionmaker(bind=read_engine)

def update_user(user_id, name):
    with WriteSession() as session:
        user = session.get(User, user_id)
        user.name = name
        session.commit()

def get_user(user_id):
    with ReadSession() as session:
        return session.get(User, user_id)

This approach adds maybe 20 lines of code and no new infrastructure. It handles 95% of read scaling needs. Only when you need to denormalize reads into a completely different shape (e.g., a search index) should you consider CQRS.

Fix 2 — the less obvious cause

The less obvious cause is using CQRS without idempotent projections. Even if you genuinely need separate read and write models, you must ensure that your projections can handle duplicate messages. Message brokers like RabbitMQ 3.12 or Apache Kafka 3.6 guarantee at-least-once delivery, not exactly-once. If your projection isn't idempotent, you'll get duplicate data or crashes.

Symptom pattern: You see intermittent UniqueConstraintViolation errors in your read database, or your read model shows duplicate entries. These errors often appear after a broker restart or a network partition, when messages are redelivered.

Fix: Make every projection idempotent by design. The simplest way is to use an upsert instead of an insert, and to include a version or timestamp in your events to ignore out-of-order messages. For example, in a Node.js 20 LTS service using PostgreSQL 16, you can use INSERT ... ON CONFLICT DO UPDATE to handle duplicates:

async function projectUserCreated(event) {
  const { userId, name, version } = event;
  await db.query(
    `INSERT INTO users_read (id, name, version)
     VALUES ($1, $2, $3)
     ON CONFLICT (id) DO UPDATE
     SET name = EXCLUDED.name, version = EXCLUDED.version
     WHERE users_read.version < EXCLUDED.version`,
    [userId, name, version]
  );
}

This ensures that even if the same event is processed multiple times, the read model ends up in the correct state. The WHERE clause prevents older events from overwriting newer ones. This pattern is essential for any CQRS system that uses event sourcing or message-based projections.

Fix 3 — the environment-specific cause

The environment-specific cause is using CQRS in a serverless or edge environment where cold starts and network latency amplify eventual consistency. In a traditional monolithic deployment, a read-after-write inconsistency might last 50–100 ms, which is often imperceptible. But in a serverless environment like AWS Lambda with arm64, cold starts can add 200–500 ms, and if your projection runs in a separate Lambda function triggered by an SQS queue, the total lag can easily exceed 2 seconds. Users notice that.

Symptom pattern: Your application works fine in staging (where you have warm containers and low traffic) but in production, users see stale data for several seconds after writes. You might see ProvisionedThroughputExceededException from DynamoDB if your read model is on DynamoDB and you're trying to read immediately after a write.

Fix: If you must use CQRS in a serverless environment, consider using a synchronous projection for critical reads. For example, you can write to both the write model and a read model in the same Lambda invocation, using a transaction if the read model is in the same database. Or, use a service like AWS AppSync with DynamoDB Streams to push updates to clients in real time, so they don't need to poll. But be aware that this adds complexity and cost. A typical serverless CQRS setup with API Gateway, Lambda, DynamoDB, and DynamoDB Streams can cost $0.50 per million requests for the read path and $1.25 per million for the write path, plus data transfer. That's often more expensive than a single RDS instance with a read replica.

How to verify the fix worked

After applying one of the fixes above, you need to verify that the problem is actually resolved. The verification depends on which fix you applied, but here are some general steps:

  1. Measure end-to-end latency. For a write followed by a read, instrument your code to log the time between the write commit and the read returning the updated value. In a healthy CQRS system with eventual consistency, this should be under 100 ms for most cases. If it's over 1 second, your projection is too slow or your broker is backed up. Use tools like OpenTelemetry to trace the flow.

  2. Check for duplicate projections. Run a query on your read database to count duplicates. For example, SELECT id, COUNT(*) FROM users_read GROUP BY id HAVING COUNT(*) > 1; should return zero rows. If it returns rows, your projections are not idempotent.

  3. Monitor broker lag. If you're using Kafka, check consumer group lag with kafka-consumer-groups --describe --group your-group. A lag of more than 1000 messages indicates that your projections can't keep up. For RabbitMQ, check the queue depth via the management API. A queue depth that keeps growing means your consumers are too slow.

  4. Load test with realistic patterns. Use a tool like k6 or Locust to simulate a user writing and then immediately reading. In a CQRS system, you should see a small percentage of reads returning stale data (if you're testing eventual consistency). If that percentage is above 1%, your system might not be suitable for CQRS. If you applied the read replica fix, you should see zero stale reads except during replica lag, which is typically under 100 ms.

How to prevent this from happening again

The best prevention is to avoid adopting CQRS unless you have a clear, measurable need. Here are some guidelines:

  • Start with a monolith and a single database. Use read replicas if you need to scale reads. Only split reads and writes when you have a domain where the read model is fundamentally different from the write model (e.g., you need full-text search or graph queries that your write database can't handle efficiently).

  • If you must use CQRS, make idempotency a first-class concern. Every projection should be idempotent. Use version numbers or timestamps in your events. Test your projections by deliberately sending duplicate messages and verifying that the read model remains correct.

  • Use the right tool for the job. If you need eventual consistency and high scalability, consider using a database that supports materialized views or change data capture (CDC) natively, like PostgreSQL with logical replication or Debezium. This can give you a read model without writing custom projection code.

  • Document your consistency guarantees. Make it clear to your team and your users what consistency they can expect. If a user updates their profile and then immediately refreshes the page, will they see the change? If not, you need to design the UI to handle that (e.g., optimistic updates).

  • Set up alerts for projection lag. Monitor the time between an event being written and it being projected. If it exceeds a threshold (e.g., 500 ms), alert. This will catch issues before users complain.

Related errors you might hit next

If you're dealing with CQRS issues, you might also encounter these related errors:

  • OptimisticConcurrencyException in your write model when two commands modify the same aggregate. This often happens when you have a distributed system without proper locking.
  • MessageDuplicationException or duplicate events in your event store. This can happen if your event store doesn't enforce idempotency.
  • ProjectionNotFoundException when a projection fails to start because it can't find its checkpoint.
  • CommandTimeoutException when a command handler takes too long because it's waiting for a read model to update.
  • ReadModelConsistencyException when your application enforces that reads must be up-to-date but the read model is behind.

These errors are all symptoms of the same underlying issue: CQRS introduces distributed system complexity. If you're seeing them frequently, it's a sign that CQRS might not be the right fit for your project.

When none of these work: escalation path

If you've tried the fixes above and you're still seeing issues, it's time to escalate. Here's a step-by-step path:

  1. Instrument everything. Add detailed logging around your command handlers, event publishers, and projections. Log the event ID, timestamp, and processing time. This will help you pinpoint where the delay or error occurs.

  2. Replay events. If your read model is corrupted, you may need to rebuild it from the event store. Most event stores (e.g., EventStoreDB 23.10) support replaying all events for a specific aggregate or stream. This can take time, but it's often the only way to recover from non-idempotent projections.

  3. Consider a hybrid approach. If CQRS is causing too many problems, you can revert to a simpler architecture for parts of your system. For example, keep CQRS for your high-volume, denormalized read model, but use direct database reads for low-volume, consistency-critical operations.

  4. Consult the community. The CQRS pattern has been discussed extensively. Look for case studies from companies like Microsoft, which documented their CQRS journey in the book "Exploring CQRS and Event Sourcing." Also, check forums like Stack Overflow for specific error messages.

  5. Hire an expert. If your team is stuck, bringing in someone who has implemented CQRS in production can save weeks of trial and error. But be wary: CQRS is often over-prescribed. Make sure the expert understands your domain and isn't just advocating for the pattern because it's fashionable.

Frequently Asked Questions

What is the difference between CQRS and event sourcing? CQRS is about separating reads from writes. Event sourcing is about storing state as a sequence of events. They are often used together, but they are distinct patterns. You can use CQRS without event sourcing (e.g., by using a message broker to update a read model), and you can use event sourcing without CQRS (e.g., by rebuilding state from events on every read). The confusion arises because many CQRS implementations use event sourcing to propagate changes to the read model.

When should I not use CQRS? Avoid CQRS when your domain is simple CRUD, when you need strong consistency for reads after writes, or when your team lacks experience with distributed systems. If your application has fewer than 10,000 daily active users and a read/write ratio below 10:1, a single database with read replicas is almost always a better choice. CQRS adds operational overhead that only pays off at scale or with complex domain models.

How do I handle transactions in CQRS? In CQRS, you typically don't have distributed transactions. Instead, you use eventual consistency and compensating actions. For example, if a command fails after partially updating the write model, you might need to emit a compensating command to undo the change. This is complex and error-prone. If you need ACID transactions across multiple aggregates, CQRS is probably the wrong pattern. Consider using a traditional relational database with transactions instead.

What are the alternatives to CQRS? Alternatives include read replicas, materialized views, change data capture (CDC), and simple caching. For example, PostgreSQL 16 supports logical replication, which can stream changes to a read-only replica. You can also use a tool like Debezium to capture changes and update a search index. These approaches give you the benefits of separate read models without the full complexity of CQRS.

Conclusion

CQRS is a powerful pattern, but it's not a default. It earns its complexity in systems with highly asymmetric read/write loads, complex domain models that benefit from separate read and write representations, and teams that are prepared to handle eventual consistency. It fails in simple CRUD applications, in environments where low latency is critical, and in teams without distributed systems experience. The errors you see — stale reads, duplicate projections, command timeouts — are signals that you might be in the latter category.

If you're currently struggling with CQRS, start by measuring your read/write ratio and your end-to-end latency. If your read/write ratio is less than 10:1, or if your latency budget for reads is under 100 ms, consider reverting to a simpler architecture. Your next step: open your application's main repository file (e.g., UserRepository.java or user_repository.py) and check whether you're using separate read and write models. If you are, measure the time between a write and a subsequent read in your test suite. If that time is over 100 ms, you have a candidate for simplification. Start there.
