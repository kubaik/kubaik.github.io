APM is blind to your AI agents

Traditional APM misses AI incidents like empty retrieval and token overruns.

There's a one-line change buried in most traditional apm setups that nobody flags until it's expensive. The tutorials all show the happy path. Here's what changed once we stopped guessing and started measuring.

The conventional wisdom (and why it's incomplete)

Application performance monitoring was built on a simple premise: a request comes in, work happens, a response goes out. Trace it, time it, alert if it's slow or errors. That model served us well for two decades of CRUD apps. But AI systems — LLM calls, agent loops, RAG pipelines — don't behave like CRUD apps. They are non-deterministic, they spawn sub-calls, they can silently degrade, and they often fail semantically rather than technically. A 200 OK response from an LLM endpoint tells you nothing about whether the answer was hallucinated, whether the agent got stuck in a loop, or whether the retrieval step returned zero relevant chunks.

The conventional wisdom says: instrument your HTTP calls, set up latency and error-rate alerts, and you're covered. That advice is incomplete because it assumes failure means an exception or a timeout. In AI systems, the most expensive failures are the ones that return a perfectly valid HTTP 200 with a plausible-but-wrong answer. Your APM dashboard stays green while your users get garbage. The part that trips people up is that traditional APM has no concept of semantic correctness, token economics, or agent state — and that's what this post actually covers.

What actually happens when you follow the standard advice

You deploy an AI agent that uses OpenAI's GPT-4o (version 2024-08-06) to answer customer questions. You set up Datadog APM 7.x, instrument the HTTP client, and configure alerts for p99 latency > 2s and error rate > 1%. Everything looks fine for weeks. Then a support manager mentions that customers are complaining about wrong answers. You check your dashboards: latency is 1.2s, error rate is 0.1%, no alerts. You dig into logs and find that 40% of responses contained hallucinated product IDs. Your APM never noticed because the API returned 200 OK with a valid JSON body.

This is not a hypothetical. A common failure mode in production RAG systems is the "empty retrieval" problem: the vector search returns zero documents, the LLM is prompted with no context, and it confidently makes something up. Traditional APM sees a successful database query (0 rows returned is not an error) and a successful LLM call. No red lights. But the user gets a wrong answer, and you lose trust.

Another gap: token usage and cost. A runaway agent loop can make 50 LLM calls in a single user request, burning through $0.10 in tokens per request instead of $0.002. Your APM might show a 5-second latency spike, but it won't tell you that you just spent 50x more than expected. You need token-level cost tracking, which most APM tools don't provide out of the box.

A different mental model

Instead of thinking about requests and responses, think about intent, execution, and outcome. For AI systems, you need to monitor:

  1. Intent accuracy — did the system understand what the user wanted? This often requires a separate classifier or a human-in-the-loop eval.
  2. Execution traces — not just HTTP spans, but the full chain of reasoning steps, tool calls, and retrieval results. OpenTelemetry's semantic conventions for GenAI (still evolving as of 2026) attempt to standardize this, but adoption is uneven.
  3. Outcome quality — was the final answer correct, relevant, and safe? This is where traditional APM completely drops the ball.

The key shift is from infrastructure metrics to semantic metrics. You still need latency and error rates, but you also need metrics like retrieval recall@k, answer faithfulness score, and token cost per request. These are not available from your APM vendor's default dashboard. You have to build them.

A practical approach: wrap your LLM calls in a custom instrumentation layer that logs the prompt, the response, token counts, and a quality score (from a small evaluator model or heuristic). Then ship those logs to a system that can alert on quality degradation. This is more work than installing a Datadog agent, but it's the only way to catch the failures that matter.

Evidence and examples from real systems

Consider a typical customer support agent built with LangChain 0.2 and OpenAI. The agent has access to three tools: search_knowledge_base, get_order_status, and escalate_to_human. In a healthy run, the agent calls search_knowledge_base, gets 3 relevant chunks, and answers. In a failure mode, the retrieval returns 0 chunks (because the query was phrased oddly), and the agent either hallucinates or calls escalate_to_human unnecessarily.

Traditional APM would show: 1 LLM call, 1 tool call, 200 OK, 800ms latency. No error. But the user experience is broken. To catch this, you need to log the retrieval result count and alert if it's 0 for more than 5% of requests. Here's a minimal Python example using OpenTelemetry to add a custom span attribute:

from opentelemetry import trace
from opentelemetry.trace import Status, StatusCode

tracer = trace.get_tracer(__name__)

def search_knowledge_base(query: str):
    with tracer.start_as_current_span("retrieval.search") as span:
        results = vector_store.similarity_search(query, k=3)
        span.set_attribute("retrieval.num_results", len(results))
        if len(results) == 0:
            span.set_status(Status(StatusCode.ERROR, "empty retrieval"))
        return results

This adds a custom attribute and marks the span as error when retrieval is empty. But note: this only works if your APM backend supports custom span attributes and can alert on them. Many don't, or charge extra for custom metrics.

Another example: token cost tracking. A common trap is to assume that all LLM calls cost the same. In reality, GPT-4o costs $2.50 per 1M input tokens and $10.00 per 1M output tokens (as of 2026). A single agent run might use 2000 input tokens and 500 output tokens, costing $0.005 + $0.005 = $0.01. If your agent loops 10 times, that's $0.10 per request. At 10,000 requests per day, that's $1,000 per day — a 10x cost overrun compared to a well-behaved agent. Traditional APM won't show this; you need to aggregate token counts per request and alert on cost per request exceeding a threshold.

Here's a JavaScript example for tracking token usage in a Node.js 20 LTS environment using the OpenAI SDK:

import OpenAI from 'openai';
import { metrics } from '@opentelemetry/api';

const meter = metrics.getMeter('ai-agent');
const tokenCounter = meter.createCounter('llm.tokens.total', {
  description: 'Total tokens used by LLM calls',
});

const openai = new OpenAI({ apiKey: process.env.OPENAI_API_KEY });

export async function callLLM(prompt, model = 'gpt-4o') {
  const response = await openai.chat.completions.create({
    model,
    messages: [{ role: 'user', content: prompt }],
  });
  const usage = response.usage;
  tokenCounter.add(usage.total_tokens, {
    model,
    prompt_tokens: usage.prompt_tokens,
    completion_tokens: usage.completion_tokens,
  });
  return response.choices[0].message.content;
}

This records token usage as a metric. You can then create alerts for when the average tokens per request exceeds a baseline (e.g., 1500 tokens). Without this, you're flying blind on cost.

The cases where the conventional wisdom IS right

Traditional APM is not useless for AI systems. It still catches:

  • Infrastructure failures: LLM API outages (e.g., OpenAI returning 503), network timeouts, rate limit errors (429). These are real and APM handles them well.
  • Latency regressions: If your p95 latency jumps from 800ms to 3s, APM will alert you. That could indicate a model change, a cold start, or a downstream dependency issue.
  • Basic error rates: If your code throws an exception because the LLM returned malformed JSON, APM catches it.

So the conventional wisdom is right for the transport layer. It's wrong for the semantic layer. You need both. The mistake is assuming that because APM covers the transport, it covers the whole system. It doesn't.

How to decide which approach fits your situation

The right level of semantic monitoring depends on your risk tolerance and the cost of a wrong answer. Use this table to decide:

Scenario Traditional APM sufficient? Additional semantic monitoring needed
Internal chatbot for FAQ Yes, mostly Low priority; occasional manual review
Customer-facing support agent No High: retrieval recall, hallucination detection
Code generation assistant No High: compilation success rate, unit test pass rate
Document summarization No Medium: factuality score, coverage of key points
Real-time translation No Medium: BLEU score, human spot-checks
AI-powered search No High: click-through rate, zero-result rate

If you're in the "No" column, you need to invest in custom instrumentation. Start with the highest-risk failure mode: for support agents, that's usually empty retrieval or hallucination. For code assistants, it's syntax errors or non-compiling code. Measure that, alert on it, and iterate.

Common objections, and responses

Objection: "We can't afford to build custom monitoring."
You can't afford not to. A single hallucination that reaches a customer can cost more in trust and support time than the engineering hours to build a simple evaluator. Start small: log the retrieval result count and token usage. That's two metrics, maybe 50 lines of code.

Objection: "Our APM vendor says they support AI monitoring."
Check what they actually measure. Many vendors have added "LLM observability" features that are just HTTP tracing with a fancy name. They still don't measure semantic quality. Ask them: can you alert on retrieval recall? Can you track token cost per user session? If not, you're still blind.

Objection: "We'll just use human evaluation."
Human evaluation is great for calibration but too slow and expensive for real-time alerting. You need automated metrics to catch regressions within minutes, not days. Use humans to label a sample and train a small evaluator model, then run that evaluator on every request.

Objection: "This is too complex; we'll just use a better model."
A better model reduces but doesn't eliminate hallucinations. Even GPT-4o can hallucinate when given no context. The monitoring gap remains.

What the alternative approach would change

If you adopt semantic monitoring, your incident response changes. Instead of waiting for a customer complaint, you get an alert: "Retrieval recall dropped from 95% to 70% in the last 15 minutes." You check the vector database — maybe an index rebuild failed, or a new document batch has a different embedding distribution. You fix it before users notice.

You also get cost visibility. A dashboard showing token cost per request, per user, per model helps you optimize prompts and choose cheaper models for simple tasks. For example, you might route 80% of queries to GPT-4o-mini ($0.15 per 1M input tokens) and only 20% to GPT-4o, cutting costs by 70% without hurting quality.

Finally, you build a feedback loop. Every request logs its inputs, outputs, and quality score. You can analyze failures, improve prompts, and retrain retrieval models. This is how AI systems get better over time — not by hoping the model improves, but by systematically finding and fixing failure modes.

Summary

Traditional APM misses the majority of AI-related incidents because it monitors transport, not semantics. To catch the failures that matter, you need to instrument retrieval quality, token cost, and answer correctness. Start by adding two metrics to your AI pipeline: retrieval result count and total tokens per request. Then set alerts for when retrieval returns zero results or token usage exceeds a baseline. This won't cover everything, but it will catch the most common and expensive failures.

Your next step: open your AI service's code and add a log line that records the number of retrieved documents and the total tokens used for each request. Deploy it, then check the logs after an hour. You'll likely find at least one surprising pattern — maybe 10% of requests have zero retrieval, or your average token count is double what you expected. That's the first incident your APM missed.

Frequently Asked Questions

How do I monitor LLM hallucinations in production? You can't directly detect hallucinations without a ground truth, but you can use proxy metrics: retrieval recall (did you retrieve relevant documents?), answer consistency (does the same question get different answers?), and factuality scores from a small evaluator model. Start by logging retrieval results and using a lightweight model like GPT-4o-mini to score answer relevance on a sample of requests. Alert if the average score drops below a threshold.

Why does my APM show no errors but users complain about wrong answers? Because APM only sees HTTP status codes and latency. A wrong answer is still a 200 OK. You need semantic monitoring to catch it. Add custom metrics for retrieval quality and token usage, and consider a periodic human evaluation to calibrate your automated scores.

What metrics should I track for a RAG pipeline? At minimum: retrieval recall@k (percentage of queries where at least one relevant document is retrieved), average number of retrieved documents, token usage per request, and answer latency. If you have ground truth, track answer accuracy. Also monitor embedding drift and index freshness.

How much does it cost to add semantic monitoring? The engineering cost is typically 20–40 hours to build a basic pipeline that logs retrieval results and token usage, plus the cost of running an evaluator model (e.g., $0.001 per request for GPT-4o-mini). For a service handling 10,000 requests per day, that's about $10 per day in evaluation costs. Compare that to the cost of a single customer-facing hallucination.
