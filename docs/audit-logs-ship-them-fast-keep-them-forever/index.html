Audit logs: ship them fast, keep them forever

Design an audit log pipeline that separates durability from searchability, with tiered retention, integrity hashing, and a cost model you can verify.

Audit logging is usually framed as a compliance checkbox: capture every event, write it somewhere immutable, retain it for years, never look at it again. That framing conflates two different requirements — durability and searchability — and the conflation is what produces both latency spikes during peak traffic and storage bills nobody budgeted for.

This article separates those concerns. It covers why the default "everything hot, forever" pipeline breaks, how to model the cost of alternatives, how to route events to tiers at write time, and how to keep integrity verifiable once data has left the hot store.

The conventional playbook and its blind spot

The standard advice looks roughly like this:

  1. Mirror every database change into a write-once table or object storage bucket.
  2. Stream the same events to a SIEM.
  3. Retain everything for the maximum period any regulation might require.
  4. Consider the problem solved.

This delivers durability and immutability. It does not deliver retrieval. Compliance obligations are usually about proving an action happened, showing the record has not been altered, and producing it within some stated window when asked. Only the third point depends on how the data is stored, and it is the one the playbook ignores.

Two failure modes follow.

Write-path amplification. If the audit write is synchronous with the business write, every request now does two writes instead of one, and the audit destination becomes a shared hotspot. Under load, tail latency on the primary path rises because unrelated requests contend for the same audit table or broker partition. The usual mitigations — sharding the audit table, buffering through a queue, throttling the stream — add complexity after the fact rather than avoiding the coupling up front.

Retention cost without query demand. A retention policy set to "keep everything, you never know" stores far more than is ever read. The asymmetry is structural: storage cost grows linearly with time, while the probability that any given byte is queried falls off sharply with age. Most audit requests concern recent activity; the long tail exists to satisfy a legal hold, not an investigation.

Modelling the cost before choosing a tier

Tiering decisions should be arithmetic, not intuition. The inputs are: ingestion rate, retention period, and the per-GB-month price of each storage class. Multiply ingestion by retention months by price.

Worked example with illustrative prices (substitute your own region's current published rates — object storage pricing changes):

  • Ingestion: 5 TB/month.
  • Retention: 84 months (7 years).
  • Steady-state volume: 5 TB × 84 = 420 TB = 430,080 GB.

At a hypothetical $0.023/GB-month for a standard infrequent-access class, the steady-state monthly cost is 430,080 × $0.023 ≈ $9,892. At a hypothetical $0.00099/GB-month for a deep-archive class, the same volume costs 430,080 × $0.00099 ≈ $426. The ratio between the two is roughly 23×, and that ratio — not the absolute numbers — is the argument for tiering.

The arithmetic also tells you when tiering is not worth it. If ingestion is 1 GB/day, steady-state volume after seven years is about 2,555 GB, and the difference between the two classes is on the order of tens of dollars per month. At that scale the operational overhead of three storage layers and a retrieval abstraction exceeds the saving.

To measure your own situation rather than estimate it:

  • Pull actual usage from your cloud cost tooling, filtered by the service and a tag applied to audit buckets, over the last 90 days.
  • Pull object counts and average object size from a storage inventory report to get true volume rather than assumed volume.
  • Instrument the write path with a histogram of audit-write latency and compare its p99 against the p99 of the business write. If they track each other under load, the audit write is on the critical path.
  • Log every retrieval request with the age of the data requested. After a quarter you will have a real distribution of query age, which is the only honest input to a retention policy.

A three-layer model

Split audit data by the job it does, not by the technology that stores it.

Layer Typical retention Retrieval characteristics Primary consumer
Hot Days to a few weeks Sub-second, indexed, ad-hoc queries On-call engineers, SOC
Warm Weeks to a year Seconds to minutes, query-in-place Incident response, spot audits
Cold Multi-year Minutes to hours, restore-then-read Regulatory holds, legal

The important property is that routing happens at write time. If you decide the tier after the fact, you have already paid to store the event hot, and you are running a batch job whose failure modes you now own. Deciding at write time means the event never enters a tier it does not belong in.

The second property is that the hot layer is bounded by query need, not by compliance need. The hot layer exists so that humans can investigate quickly. The cold layer exists so that a regulator can be satisfied eventually. Conflating them is what makes the hot layer expensive.

Integrity in a tiered pipeline

The objection to tiering is usually about tamper-evidence: if data moves between storage classes, how do you prove it was not altered?

The answer is to make integrity a property of the record, not of the storage medium. Compute a digest of the event's canonical serialization at write time and store that digest somewhere durable and separate. On retrieval, recompute the digest and compare. If the storage layer altered the bytes, the digests diverge regardless of which tier the object sat in.

Two details matter:

  • Canonicalization. Hash a deterministic serialization — sorted keys, fixed number formatting, explicit encoding. Hashing JSON.stringify output from an arbitrary object is not reproducible across languages or key orders.
  • Digest storage. Keep the digest in a store with different access controls and a different failure domain from the log objects themselves. A digest stored alongside the object it protects provides no protection against an attacker who can write to that bucket.

Object-lock features in object storage (retention modes that prevent deletion or overwrite for a defined period) are a useful complement, but they solve a different problem: they prevent premature deletion, not undetected modification.

Routing events at write time

A minimal router needs three inputs: event type, a risk or sensitivity classification, and the event timestamp. The classification should come from the producer, not be inferred by the router, because only the producer knows what the event means.

The Node example below writes to a tier-selected bucket and emits a notification. Note the fixes relative to a naive version: the key uses the event's own identifier rather than an undefined property, the timestamp used for routing is the event timestamp rather than wall-clock time at the router, and the body is actually compressed if it is labelled as compressed.

// retention-router.mjs
import { gzipSync } from 'node:zlib';
import { S3Client, PutObjectCommand } from '@aws-sdk/client-s3';
import { EventBridgeClient, PutEventsCommand } from '@aws-sdk/client-eventbridge';

const s3 = new S3Client({ region: process.env.AWS_REGION });
const eb = new EventBridgeClient({ region: process.env.AWS_REGION });

const HOT_BUCKET = process.env.HOT_BUCKET;
const WARM_BUCKET = process.env.WARM_BUCKET;
const COLD_BUCKET = process.env.COLD_BUCKET;

const WARM_AFTER_MS = 7 * 24 * 3600 * 1000;
const COLD_AFTER_MS = 90 * 24 * 3600 * 1000;

function pickBucket(eventTimeMs, riskScore) {
  const age = Date.now() - eventTimeMs;
  if (riskScore >= 7) return HOT_BUCKET;      // sensitive: always hot
  if (age >= COLD_AFTER_MS) return COLD_BUCKET;
  if (age >= WARM_AFTER_MS) return WARM_BUCKET;
  return HOT_BUCKET;
}

export const handler = async (event) => {
  const body = JSON.parse(event.body);
  const { eventId, eventType, riskScore = 0, timestamp } = body;

  const eventTimeMs = Date.parse(timestamp);
  if (Number.isNaN(eventTimeMs)) throw new Error('invalid timestamp');

  const bucket = pickBucket(eventTimeMs, riskScore);
  const day = new Date(eventTimeMs).toISOString().slice(0, 10);
  const key = `audit/${day}/${eventId}.json.gz`;

  await s3.send(new PutObjectCommand({
    Bucket: bucket,
    Key: key,
    Body: gzipSync(Buffer.from(JSON.stringify(body))),
    ContentEncoding: 'gzip',
    ContentType: 'application/json',
    Metadata: { retention: bucket === HOT_BUCKET ? 'hot'
                        : bucket === WARM_BUCKET ? 'warm' : 'cold' }
  }));

  await eb.send(new PutEventsCommand({
    Entries: [{
      Source: 'audit.router',
      DetailType: 'AuditEventStored',
      Detail: JSON.stringify({ bucket, key, eventId })
    }]
  }));
};

Two operational notes. First, routing on the event's own timestamp rather than arrival time means a late-arriving event lands in the correct tier instead of being promoted to hot by accident. Second, the risk-score override is deliberate: an event that is sensitive enough to investigate should never be cold, regardless of age.

Reading across tiers

A reader abstraction hides the tier boundary from callers. The Python example below dispatches by age. It is deliberately explicit about the limitation of query-in-place: object-storage SQL selection works on line-delimited, uncompressed-or-gzip data and is not a substitute for an index, so warm queries should be scoped tightly by prefix.

from datetime import datetime, timedelta
import json
import boto3
from elasticsearch import Elasticsearch

class AuditReader:
    def __init__(self, es_host, bucket):
        self.es = Elasticsearch(es_host)
        self.s3 = boto3.client("s3")
        self.bucket = bucket
        self.hot = timedelta(days=7)
        self.warm = timedelta(days=90)

    def read_events(self, start: datetime, end: datetime):
        age = datetime.now(start.tzinfo) - start
        if age <= self.hot:
            return self._hot(start, end)
        if age <= self.warm:
            return self._warm(start, end)
        return self._cold(start, end)

    def _hot(self, start, end):
        body = {"query": {"range": {"timestamp": {
            "gte": start.isoformat(), "lte": end.isoformat()}}}}
        res = self.es.search(index="audit-hot-*", body=body, size=1000)
        return [h["_source"] for h in res["hits"]["hits"]]

    def _warm(self, start, end):
        prefix = f"audit/{start.date().isoformat()}/"
        expr = ("SELECT * FROM s3object s WHERE s.timestamp >= "
                f"'{start.isoformat()}' AND s.timestamp <= '{end.isoformat()}'")
        paginator = self.s3.get_paginator("list_objects_v2")
        out = []
        for page in paginator.paginate(Bucket=self.bucket, Prefix=prefix):
            for obj in page.get("Contents", []):
                resp = self.s3.select_object_content(
                    Bucket=self.bucket,
                    Key=obj["Key"],
                    ExpressionType="SQL",
                    Expression=expr,
                    InputSerialization={
                        "JSON": {"Type": "LINES"}, "CompressionType": "GZIP"},
                    OutputSerialization={"JSON": {}},
                )
                for ev in resp["Payload"]:
                    if "Records" in ev:
                        out.append(json.loads(ev["Records"]["Payload"]))
        return out

    def _cold(self, start, end):
        # Restore from archive, then read. Restore is asynchronous.
        raise NotImplementedError("implement restore-then-read")

The cold path is intentionally unimplemented here because it is a workflow, not a query: you submit a restore request, wait for the object to become readable, then read it and verify its digest. Treating it as a synchronous call is how teams end up with a reader that times out during an audit.

When the all-hot approach is still correct

Tiering is not universally better. Two situations favour keeping everything hot:

Regulators with short retrieval windows. If the obligation is to produce any record within hours, the cold tier's restore latency is a liability. In that case keep the full retention window in a queryable class and accept the cost — or negotiate the retrieval SLA explicitly in your policy so the constraint is documented rather than assumed.

Low volume. Below roughly a few GB per day, the absolute saving from tiering is small and the operational surface — three buckets, lifecycle rules, a restore workflow, digest verification — is real. A single bucket with a lifecycle transition and no reader abstraction is often the better engineering choice.

A related failure mode: tiering everything to the coldest class to minimise cost, then discovering that routine audit requests are now restore operations. Tiering is a cost lever. It is not a compliance lever, and it does not change what you are obliged to produce.

A decision checklist

Work through these before committing to a design:

  1. What is peak ingestion, in bytes per second, not per day? Peak determines write-path design; average determines cost.
  2. Is the audit write synchronous with the business write? If yes, quantify the tail-latency impact before adding tiers — decoupling may matter more than storage class.
  3. What is the distribution of retrieval age? Measure it for a quarter. Retention policy should follow this, not precede it.
  4. What is the worst-case retrieval SLA you must meet? This sets the floor on how cold the coldest tier can be.
  5. Can you verify integrity without the storage layer's cooperation? If not, fix that before tiering.
  6. What is the monthly cost ceiling, and what fraction of infrastructure spend is audit storage today? A tiering project should have a target number attached.
  7. Who owns the restore workflow, and has it been exercised? An untested restore path is not a retention strategy.

Failure modes to design against

Late events promoted to hot. Routing on arrival time rather than event time sends backfilled events to the most expensive tier. Route on event time; use arrival time only for monitoring.

Digest drift. If canonicalization changes between the writer and the verifier — a library upgrade that changes number formatting, for example — every historical digest fails. Version the canonicalization scheme and record the version alongside the digest.

Lifecycle rules that fight the router. If the router writes directly to a warm bucket and a lifecycle rule also transitions that bucket, objects can move twice. Pick one mechanism: either the router decides the tier and lifecycle handles expiry, or the router writes hot and lifecycle handles all transitions. Mixing both without a clear owner produces surprising bills.

Unbounded hot queries. A reader that fans out across every hot index for a wide time range will eventually take down the cluster. Enforce a maximum range on the hot path and reject queries that exceed it, rather than letting them run.

Restore storms. A legal hold that requires thousands of cold objects at once will queue behind per-object restore limits. Batch and prioritise, and keep a record of what has already been restored.

FAQ

How do you reduce object storage cost for audit logs without breaking compliance? Measure first: pull 90 days of cost data filtered by the audit tag, and pull an inventory report for true object counts and sizes. Then model the saving from moving data older than your measured query horizon to a colder class. The compliance constraint is the retrieval SLA, not the storage class — so document the SLA, then choose the cheapest class that meets it.

What retention period applies to audit logs in financial services? It varies by jurisdiction and licence, and no general answer is safe. What is consistent is the shape: a long retention obligation combined with a much shorter searchable window. Establish both numbers in writing — how long records must exist, and how quickly they must be produced — because only the second constrains your storage design.

How do you detect tampering in a tiered pipeline? Hash a canonical serialization of each event at write time and store the digest separately from the object. Recompute on retrieval and compare. Storage-class transitions preserve bytes, so a digest computed at ingest remains valid across tiers. The digest store needs different access controls from the log store, or it protects nothing.

What can replace a full SIEM for hot audit search? A managed search service, a date-partitioned relational table, or a dedicated search engine all work for the hot window. The choice matters less than the boundary: cap the hot window at your measured query horizon and archive beyond it. A smaller hot index is cheaper to run and faster to query than a large one, so the boundary is a performance decision as much as a cost one.

Does object lock replace integrity hashing? No. Object lock prevents deletion or overwrite for a retention period. It does not detect modification made through a path that the lock does not cover, and it says nothing about data that has already been copied elsewhere. Use it for immutability guarantees and hashing for integrity guarantees; they are complementary.

Do this next

Open your object storage console, run an inventory report on the bucket that holds your audit data, and write down two numbers: total bytes, and bytes last modified more than 90 days ago. That second number is the volume currently sitting in your most expensive tier that almost certainly does not need to be there. You now have the input to a lifecycle rule and a defensible estimate of what tiering would save — before you write any router code.
