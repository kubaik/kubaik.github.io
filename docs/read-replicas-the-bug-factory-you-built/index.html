Read replicas: the bug factory you built

Read replicas lag by design. Learn how to classify reads, route freshness-critical queries to the primary, and measure your exposure to stale reads.

Read replicas are often introduced as free capacity. A second instance is added, read traffic is pointed at it, and dashboards go green. Weeks later, a user reports that a profile picture reverted to an older version, or that an order placed moments ago is missing from order history. The replica did not fail. It did exactly what it was designed to do. The defect lives in the assumption that a replica is a read-only copy of the primary at all times. It is not. It is a copy that lags, sometimes by milliseconds and sometimes by minutes, and that lag is invisible to application code until it produces a user-visible inconsistency.

The problem this article addresses: how to find and fix the read-after-write inconsistencies that read replicas introduce before users report them.

The gap between documented behavior and application needs

Documentation for managed databases typically describes replication as asynchronous and notes that replicas may lag. That is accurate and of limited use for application design. The documentation describes the mechanism; it does not say which queries can tolerate stale data and which cannot. That classification is an application-level decision, and it is frequently never made explicitly. Instead, reads are routed to replicas by default — often at the ORM, connection-pooler, or proxy layer — with no consistency plan.

The counterintuitive part is that bugs caused by stale reads rarely look like data-freshness bugs. They surface as authorization failures, duplicate submissions, phantom 404s, and "impossible" state transitions. A user updates an email address, then immediately tries to log in with the new address and receives "invalid credentials" because the auth service read from a replica that had not caught up. A payment webhook reads an order from a replica, does not yet see the status change, and reprocesses the charge. These are not replica failures. They are read-after-write violations, and they are endemic to any system that separates writes from reads without a consistency plan.

How read replicas work under the hood

A read replica is a second database instance that receives a stream of changes from the primary. In PostgreSQL, that stream is WAL (write-ahead log) records shipped to the replica, which replays them. In MySQL, it is the binary log. Managed services generally use variants of this model. The key property is that replication is asynchronous by default: the primary commits a transaction and acknowledges the client before the replica has applied it. The replica applies changes as fast as it can, but there is no bound on the delay.

That delay is replication lag. It can be near-zero on an idle system and spike under load. A long-running transaction on the primary, a bulk load, a network interruption, or a replica that falls behind on IO can all push lag from milliseconds to minutes. The replica remains healthy by most monitoring definitions — it is up, connected, and applying WAL — but it is not caught up.

The primary has no knowledge of which replica has applied which transaction unless it is asked. PostgreSQL exposes this through pg_current_wal_lsn() on the primary and pg_last_wal_replay_lsn() on the replica; the difference is the replay lag in bytes. MySQL exposes SHOW REPLICA STATUS with Seconds_Behind_Source. These are the numbers that matter for consistency decisions, and they are rarely wired into application logic.

Three strategies for consistency-aware read routing

The fix is not to abandon replicas. It is to make the read path aware of what each read requires. There are three practical strategies, and most systems need a mix.

1. Route reads that follow a write back to the primary

This is the simplest and most effective fix. If a request writes and then reads the same entity, that read must go to the primary — or at least to a replica known to have applied the write. In practice, teams implement this with a "sticky primary" window: after a write, the same session or request context routes reads to the primary for a short period. The window is a heuristic, not a guarantee, but it eliminates the most common user-facing inconsistency.

A minimal implementation in Python with SQLAlchemy:

from contextlib import contextmanager
from sqlalchemy import create_engine
from sqlalchemy.orm import sessionmaker

primary_engine = create_engine("postgresql://app@primary/db")
replica_engine = create_engine("postgresql://app@replica/db")
PrimarySession = sessionmaker(bind=primary_engine)
ReplicaSession = sessionmaker(bind=replica_engine)

@contextmanager
def read_session(after_write: bool = False):
    # after_write is set by the request handler when the same request
    # performed a write to the entity being read.
    factory = PrimarySession if after_write else ReplicaSession
    session = factory()
    try:
        yield session
    finally:
        session.close()

The hard part is not the code — it is threading after_write through request handlers. That requires knowing which reads are causally dependent on which writes. A common pattern is to set a flag on the request context when any write occurs and have the data-access layer consult it. This is coarse (it sends all reads in that request to the primary) but correct.

2. Wait for the replica to catch up to a known LSN

When a read must come from a replica but must see a specific write, the primary's WAL position can be captured at write time and the replica polled until it reaches that position. PostgreSQL makes this possible with pg_current_wal_lsn() and pg_last_wal_replay_lsn(). The write path records the LSN; the read path polls the replica until its replay LSN is at least that value, with a timeout.

-- On the primary, immediately after the write transaction commits:
SELECT pg_current_wal_lsn();

-- On the replica, before serving the read:
SELECT pg_last_wal_replay_lsn() >= '0/16B6C50'::pg_lsn;

This is precise but adds latency: the read waits for replication, which is exactly the delay the replica was meant to avoid. Use it for reads where correctness matters more than a few milliseconds — for example, reading back a just-created resource in an API response.

3. Make the read idempotent and tolerate staleness

Some reads genuinely do not need freshness. A product listing, a public profile, or a feed of posts can be seconds stale without anyone noticing. The mistake is treating all reads the same. Classify them. Reads that feed into a write decision (for example, checking a balance before a debit) must be fresh. Reads that are purely presentational can be stale. Document the classification in code, not in a wiki that nobody reads.

How to measure lag and your exposure to stale reads

Replication lag is the metric that matters, and it should be monitored per replica, not in aggregate. On PostgreSQL, a query like this on the replica gives the replay delay in seconds:

SELECT
  now() - pg_last_xact_replay_timestamp() AS replication_delay;

The number itself is not the problem; the problem is that application code has no visibility into it. If the read path does not know the current lag, it cannot decide whether a stale read is acceptable.

A useful exercise: instrument read endpoints with a counter for "read served from a replica where the client had written to the same entity within the last N seconds." That counter is a direct measure of exposure to read-after-write bugs. It should be zero for critical paths. If it is not, a bug has been found before a user reports it.

To measure precisely rather than by intuition, instrument three things and compare them over a representative window (for example, one week of production traffic or a load test):

  1. Per-replica lag, sampled every few seconds, recorded as a time series with percentiles (p50, p95, p99, max). Lag is bursty, so the maximum and p99 matter more than the average.
  2. The stale-read counter above, broken down by endpoint and by whether the endpoint is user-facing.
  3. The primary's write volume and longest transaction duration, so lag spikes can be correlated with their cause.

The comparison to make is between the stale-read counter on critical endpoints and zero. Any non-zero value on a path where correctness matters is a defect, regardless of how good the lag percentiles look.

The failure modes that are easy to miss

The obvious failure mode is a user not seeing their own write. The less obvious ones are worse because they corrupt state rather than merely confuse a user.

Duplicate side effects. A worker reads a job from a replica, sees status pending, and starts processing. The primary had already marked it completed a moment earlier, but the replica had not caught up. The worker processes it again. If the job is not idempotent, a customer is charged twice or a duplicate email is sent. This is a read-after-write violation in a background process, and it is common because workers are often pointed at replicas to offload the primary.

Authorization bypass. A user's role is revoked in the primary. A request hits a replica that still shows the old role and grants access. The window is small, but for sensitive operations it is a real security gap. Permission checks are reads, and they are almost always routed to replicas.

Phantom 404s. A resource is created, and the client immediately fetches it by ID. The read goes to a replica that has not seen the insert, and the API returns 404. The client may retry, may show an error, or may cache the 404. From the user's perspective, the create succeeded but the resource does not exist.

Broken pagination. A list endpoint reads from a replica while writes are happening on the primary. Pages can skip or duplicate items because the underlying data changed between requests. This is a consistency problem even without replicas, but replicas widen the window.

Silent data loss in read-modify-write cycles. An application reads an entity from a replica, modifies it, and writes it back to the primary. If the replica was stale, the write overwrites newer data with older data. This is the most dangerous failure mode because it is a lost update that no error surfaces.

A worked example makes the lost-update case concrete. Suppose a counter row starts at 10. A request reads it from a replica that is one transaction behind and sees 10. Meanwhile the primary increments it to 11 and commits. The request adds one to its stale value and writes 11 back to the primary. The correct value was 12; the primary now holds 11. No error is raised, no constraint is violated, and the drift is invisible until someone reconciles the numbers. The mitigation is either to route the read to the primary, to perform the increment as a single atomic statement (UPDATE counters SET value = value + 1) so no read is needed, or to attach a version column and reject writes based on stale versions.

Tooling categories and what they do and do not solve

A custom proxy is not required, but a layer that understands read/write intent is. Several categories of tooling are worth evaluating:

  • Connection poolers with routing rules. PgBouncer and ProxySQL can route queries based on statement type, but they generally cannot know whether a read follows a write in the same logical operation. They are useful for load balancing, not for consistency.
  • ORM-level read/write splitting. Some ORMs and database toolkits support a primary/replica configuration with a "sticky" option that routes reads to the primary after a write within the same transaction or session. Quality varies; check whether stickiness is per-transaction or per-request, and whether it covers reads in separate requests.
  • Managed database proxies. Services such as Amazon RDS Proxy can route to replicas, but they do not solve read-after-write consistency; they make the routing configurable. Read the documentation carefully on what guarantees they do and do not provide.
  • Application-level session stores. If a session or request context already exists, storing the last-write timestamp or LSN there is a lightweight way to make routing decisions without new infrastructure.

The tooling matters less than the discipline of classifying reads. A team that knows which reads are freshness-sensitive can implement routing with a few lines of code; a team that does not will struggle regardless of the proxy.

When this approach is the wrong choice

Read replicas are not always the answer, and adding consistency logic is not always worth it. If the workload is write-heavy and read-light, a replica may add cost and complexity without relieving much pressure. If the application is already tolerant of stale reads by design — for example, an analytics dashboard that refreshes every few minutes — the consistency work is unnecessary. And if the primary is not actually saturated, adding a replica may just move the bottleneck to replication lag without improving throughput.

The more interesting question is whether a replica is needed at all. Vertical scaling of the primary, query optimization, and caching can often absorb read load without introducing a second source of truth. A replica is a tool for scaling reads and for failover, not a default architecture. Teams that add one because it is the standard pattern often inherit the consistency bugs without needing the capacity.

Common production pitfalls and what they cost

Pitfall: assuming lag is always milliseconds. It usually is, until it is not. A bulk migration or a long transaction can push lag to minutes. If the application has no timeout on "wait for replica," it can hang. Always bound the wait and fall back to the primary.

Pitfall: monitoring replica health, not replica freshness. A replica that is up but an hour behind is healthy by uptime checks and useless for reads. Alert on lag, not just availability.

Pitfall: testing against a single database. Integration tests that run against one instance never exercise the read-after-write path. If a replica cannot run in CI, at least write a test that simulates stale reads by injecting a delay or a mock that returns old data.

Pitfall: forgetting background workers. Cron jobs and queue consumers are often pointed at replicas to reduce primary load. They are also the most likely to perform read-modify-write cycles. Audit them separately.

Pitfall: believing the ORM handles it. Some ORMs advertise automatic read/write splitting. Read the fine print: many route based on whether a transaction is open, not on whether the specific entity was just written. A read in a new transaction after a write in a previous one may still go to the replica.

A decision checklist for each read path

For every read in the data-access layer, answer these questions in order:

  1. Does this read ever need to reflect a write from the same user or process within the last few seconds? If yes, route it to the primary or implement a wait-for-LSN check.
  2. Does this read feed into a write decision — a balance check, an authorization check, a job-status check before processing? If yes, treat it as freshness-critical even if no recent write is expected, because a stale read can corrupt state.
  3. Is the read purely presentational — a listing, a public profile, a feed? If yes, a replica is appropriate, and the acceptable lag should be stated explicitly in the code or configuration.
  4. Is the read part of a read-modify-write cycle? If yes, prefer an atomic update on the primary over reading and writing back, or add a version column to detect stale reads.
  5. Is the wait bounded? Any logic that waits for a replica must have a timeout and a documented fallback.

Frequently Asked Questions

How can an application be checked for read-after-write bugs? Instrument reads that occur shortly after writes to the same entity and count how many are served by a replica. If the count is non-zero for user-facing flows, there is exposure. Assertions in staging that compare replica and primary results for critical reads also help.

Can synchronous replication be used to avoid this entirely? Synchronous replication ensures the primary waits for at least one replica to acknowledge each commit before returning. That eliminates lag for that replica, but it adds write latency and reduces availability if the replica is slow or unreachable. It is a valid choice for some systems, but it does not solve the routing problem: the read still needs to go to the replica that has the data.

Why does ORM read/write splitting not fix this? Most ORM splitting is based on transaction boundaries or explicit hints. It cannot infer that a read in a new request depends on a write from a previous request. Consistency is an application concern, not a driver concern.

What is a safe replication lag threshold? There is no universal number. The threshold should be derived from the application's tolerance for stale reads. For a read that must reflect a write from the same user session, the tolerance is effectively zero, so route to the primary. For presentational reads, a lag of several seconds may be fine. Measure the lag and set alerts relative to the reads that matter.

What to do next

Open the data-access layer and find every place a read is routed to a replica. For each one, apply the decision checklist above, starting with the read that follows a user profile update — that is the one most likely to be reported as a bug. Then add a counter for replica reads that follow a write in the same request context and watch it for a day. That counter is the early warning system, and adding it takes less than thirty minutes.
